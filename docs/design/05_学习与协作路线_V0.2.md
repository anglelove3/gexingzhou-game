# 葛行舟｜游戏优先的学习与协作路线

V0.2｜2026-10-03｜不是逐文件实施计划

## 1. 当前时间基线

沿用预计2027年6月毕业，原交接档案为2026年8月。本轮从2026年10月重新排期，不能把旧“研二下”“剩余六个月”当当前事实。每周原计划20—30小时可作预算，遇到论文/实验高峰应降低内容范围，不以熬夜硬补。

25小时示例：15小时游戏/C#，6小时AI与数据，4小时Git/作品整理/求职。先让首段能运行，再做数据可视化；没有可用事件就不训练模型。预算为协作建议，不保证交付日期或薪资。

## 2. 阶段产物与学习映射

| 阶段 | 游戏产物 | 学习内容 | 可用于求职的证据 |
| --- | --- | --- | --- |
| 当前设计 | 总案、数值、关卡与来源台账 | 范围控制、状态、时间预算 | 能解释取舍的设计稿 |
| 首段机制 | 门口移动、邀请、交互、任务 | C#类/方法/事件、Godot节点、状态机 | 可运行灰盒与测试日志 |
| 首段闭环 | 汤店回忆、返回、存档 | 场景上下文、集合去重、版本化数据 | Windows试玩、读档演示 |
| 首段体验 | 提示、可读UI、原型美术 | 输入抽象、可用性、资源管理 | 前后版本比较与玩家访谈 |
| 数据小项目 | 首段本地事件→清洗→SQL | schema、ETL、缺失/重复检查 | 匿名样本、查询、可复现报告 |
| 三日增量 | 家庭取舍、轻动作、试音、婚礼 | 调度、依赖图、战斗状态机 | 多路径验收与设计复盘 |
| AI独立小样 | 空心人有限话题实验 | 检索、事实约束、超时回退、评估 | 离线对照集、失败案例，不替代人工主线 |

实际小数据项目不包装成百万级大数据。要展示批处理/流处理时用明确标注的模拟数据，写清规模和机器条件，不伪造真实用户量。算法学习先解释任务拓扑、事件顺序、集合幂等和有限状态机如何解决本项目问题。

## 3. 参考节奏

10月先完成VS01设计评审与工程验证；随后按首段实施计划推进，具体周目标在批准设计后编写。11—12月争取可演示首段与第一份数据分析；2027年1—3月逐章扩展三日Demo；4—5月优先修复、作品集和求职，不因“还有新NPC”一直推迟可投递版本。以上是阶段目标，节假日、论文与测试结果变化时重估。

求职整理不等完整版：做一份经历总库，之后分别裁出游戏策划、游戏客户端、数据/AI应用简历。一次投递突出岗位所需证据，不能将所有方向平均堆在一页。1万元以上与双休是用户偏好，不在本轮承诺岗位现实条件；正式筛岗位时再查询当期信息。

## 4. 一对一协作

新概念：先解释在本游戏里用来解决什么→给小骨架→用户完成一小段→一起验证。复习：用户先尝试，卡住才逐步给提示。每次只问一个会实质改变当前阶段的问题，不再重新问已明确的角色、平台或主题。

代码实施时每个完成项写：运行方式、实际测试命令/结果、用户如何重现、暂缺什么。用户想先拿到可玩结果时可由Codex做主体实现，但仍给关键模块说明，不把整个项目变成无法理解的黑箱。

## 5. 仓库与公开边界

本轮没有初始化或上传远程仓库。后续完整项目使用私有仓库；公开作品版本删去真实人物照片、家族关系原件、原始聊天与未经批准的故事资料。公开技术演示使用化名与合成测试数据。

Git学习从小而具体的提交开始：一个功能/一次数值调整一个提交，说明原因与验证。不要“把整个E盘上传”；先核查实际项目根目录、忽略Godot缓存、构建产物、私人资料与临时文件。没有用户明确授权，不公开仓库或上传文件。
